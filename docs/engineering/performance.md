# 性能基线

**项目**: react-router-cossui | **最后更新**: 2026-11-18

> 本页只写对脚手架成立的约束与判断依据。业务页面落地后按真实数据补测，不把外部站点的百分比当结论。
> 数据来源：同类 SSR 站点的线上实测（Lighthouse + 体积拆解），结论按「可迁移」筛选过。

## 1. 首屏预算

按顺序花预算：HTML 体积 → 首屏图片 → 字体 → JS。

| 项              | 约束                                              |
| --------------- | ------------------------------------------------- |
| loader 返回字段 | 只返回首屏要渲染的字段，完整数据走分页或独立接口  |
| 列表首屏条数    | 一屏能看到多少就返回多少，其余由客户端增量加载    |
| 首屏图片        | 首图立即加载（`priority`），其余 `loading="lazy"` |
| 全量数据进 HTML | 禁止。序列化后的数组会变成 HTML 属性，压缩率极低  |

**为什么**：SSR 站点的 HTML 膨胀主要来自「把整份数据集塞进页面」，不是来自标记本身。这类数据熵高、几乎不可压缩，并且 Googlebot 只解析前 2 MB（按解压前计算）。同一份数据由客户端分页拉取时，第二轮请求可缓存、可并发。

## 2. HTML 体积的三个来源

按收益排序处理，不要跳步：

1. **序列化数据**（`props` / 内联 JSON）：去掉后压缩载荷通常降一半以上。属性里是 id、标题、数值，全是唯一值。
2. **重复的长类名串**：一条 300+ 字符的表格单元格类名重复几百次，压缩后几乎免费，但会让 raw 体积翻倍。收到语义类或收敛到组件里。
3. **类名本身**：最后再考虑。类名在 HTML 里高度重复，gzip / brotli 已经吃掉；改名的真实收益在 CSS 选择器一侧，且要同时改 HTML 与产物。

不值得做：短属性名、去引号、`@property` 裁剪、为体积更换样式引擎。

## 3. 长列表与长文档

先判断是哪一层的成本，再选手段：

| 手段                                                 | 省什么           | 代价                                               |
| ---------------------------------------------------- | ---------------- | -------------------------------------------------- |
| 减少同时存在的内容（折叠、分页、默认只挂载一种视图） | 全部成本，最直接 | 改变阅读与检索方式，需要产品决定                   |
| 分块 + `content-visibility: auto`                    | 首次布局         | 占位高度是估算值，锚点会漂；滚动光栅收益不明显     |
| 虚拟列表                                             | DOM 与视口成正比 | 浏览器内查找、选中、锚点、焦点、屏幕阅读器都要重建 |
| 正文 SSR / 预取                                      | 首屏等待         | HTML 变大，同一份内容出现两次（props 与 DOM）      |

- 默认选「减少内容」，其次渐进渲染，虚拟化放在最后。
- 需要浏览器内查找与标题锚点的内容页不做虚拟化。
- `content-visibility` 的价值在首次布局，不是线性滚动时的绘制；开启后必须验证目录跳转落点。
- 常驻栏（顶栏、吸顶目录、底部标签栏）不加 `backdrop-filter`：Chromium 对 fixed / sticky + `backdrop-filter` 的滚动闪烁是已知缺陷。层级用实色 Token 背景与亮度差建立。

## 4. 字体

- 不自托管 CJK webfont。一个中文变量字体带 100 个左右 `unicode-range` 子集，首屏命中几十个文件，动辄 2 MB 以上，而压缩收益为零。
- 拉丁走 `Inter Variable`，中文走系统栈：字体栈见 `app/app.css` 的 `--font-sans-stack`。
- 字体栈顺序有意义：简中系统字体要排在日文字体之前，否则 Windows 上用 `Yu Gothic UI` 渲染简体字。
- 等宽字体只用于 id、路径与代码（`--font-mono-stack`）。

## 5. 图片与 LCP

- **不要用 `opacity: 0` 门控首屏图**：完全透明的元素不计入 LCP，会把 LCP 推到水合之后。首帧直接可见，淡入只用于之后换 `src`。
- 首屏图给 `width` / `height` 或固定比例容器，避免 CLS。
- 列表缩略图限制解码宽度与并发数（`useFileThumbnails` 是参考实现：128px 宽、最多 3 并发）。
- 首屏图设 `fetchpriority="high"`，其余保持 `lazy`。

## 6. 缓存

| 资源                 | 建议                                                                |
| -------------------- | ------------------------------------------------------------------- |
| 构建产物 `/_astro/*` | `max-age=31536000, immutable`（部署平台默认）                       |
| 公开 API 响应        | `Cache-Control: public, max-age=3600, stale-while-revalidate=86400` |
| 需要鉴权的响应       | `Cache-Control: private, no-store`                                  |
| 用户上传 / 派生图    | 一年 immutable；对象存储侧的头的配置位置与代码无关                  |

## 7. 验证方式

```bash
bun run build
bun run test
```

- 体积与性能数字必须来自真实构建或线上环境；本地 `dev` 不压缩，只能做相对比较。
- 报告写清预设（desktop / mobile、CPU 降速、网络节流）与测试日期；不同预设的分数不可直接比较。
- 只改一处时不要用单次 Lighthouse 分数下结论，重复跑取中位数。
